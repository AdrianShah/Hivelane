# DRAFT — needs a decision: pricing

**Nothing on this page is decided, announced or built.** It restates the
pricing model proposed in the project plan, lists what has to be decided,
and lists the code each paid feature would need. Billing, accounts and a
hosted relay do not exist today. No launch copy mentions paid plans; the
Product Hunt pricing field says "Free". Do not build a pricing page from this.

## The proposed model

| Tier | Price | Includes |
|------|-------|----------|
| Free, forever | $0 | The CLI and every agent adapter; self-hosting the relay and dashboard (all of it, Apache-2.0); the hosted relay for rooms of up to 5 members |
| Team | about $8 per user per month | The hosted relay with longer history, analytics, Slack integration, and more members per room |
| Enterprise | Contact sales | SSO and SCIM, audit logs, end-to-end encryption key management, on-prem support, an SLA |

## What exists today, per feature

Facts from the code at commit `28594f8`, plus work visible but uncommitted
in the working tree on 2026-10-06 (marked *in progress*; it may change or
not land).

| Feature | Today |
|---------|-------|
| Accounts, organisations, seats | None. A room is an 8-character code; a member's identity is a display name they choose. The room's creator holds an owner token and can require approval for newcomers. |
| Hosted relay | None. `hivelane.dev` does not resolve (checked 2026-10-06). |
| Members per room | Hard-coded maximum of 6 (`MAX_MEMBERS`, `server/room_manager.py`). A member is one daemon connection for one checkout, which is closer to "an agent identity" than to "a person". |
| History | The relay keeps only room codes, room settings and access records durably; recent edits are swept after the warn window, and the dashboard's history lives in the browser tab. *In progress:* opt-in room history for a replay view (`server/history.py`, a `history_hours` room setting, bounded by event count, size and age; e2e rooms keep only ciphertext and hashes). |
| Analytics | Aggregate Prometheus counters on the relay (`/metrics`: edit checks by decision and scope, votes by scope, rooms, members), deliberately without room codes or names. Per-room analytics exist only in the dashboard, for the current browser session. |
| Slack integration | None committed. *In progress:* owner-configured webhooks that post a room's blocks, warnings, conflict alerts and join requests to Slack, Discord or any HTTPS endpoint (`server/webhooks.py`, with SSRF checks). |
| SSO, SCIM | None; there is nothing to sign in to. |
| Audit logs | None. Relay logs are operational JSON lines (they include room codes, names and the paths of warn/block decisions, never prompts or diffs) and are not per-tenant or tamper-evident. |
| E2E key management | One passphrase per room, generated by the first member and shared out of band (`hivelane key show` / `hivelane key set`). No rotation (a new key means a new room), no revocation, no per-member keys, no KMS. |
| On-prem | The Docker image, a Helm chart, Compose with Caddy, and Fly, Render and Railway configs; multi-instance with Redis. No support process or release-support policy beyond `SECURITY.md`. |
| SLA | Nothing to attach one to: no hosted service, no status page, no on-call. |

## Code each paid feature needs

Sizes are rough guesses (S: days, M: one to three weeks, L: more) to help
order the decision, not estimates to plan against.

| Feature | Needs | Size |
|---------|-------|------|
| **Accounts and orgs** (prerequisite for every paid feature) | Sign-in for the dashboard and a device-code login for the CLI (token stored in the personal config, like owner tokens today); organisations and membership; rooms owned by an org; the relay checking membership on join in addition to the room code | L |
| **Billing** | A payment processor integration: checkout, subscription state from its webhooks, seat counting, invoices, tax, failed-payment handling; entitlements the relay can check quickly on join | L |
| **Member limits per plan** | `MAX_MEMBERS` becomes a per-room value from the owner's entitlement; a "room full" message that says why; a decision on what counts as a member (below) | S, after accounts |
| **Longer history** | Builds on the in-progress room history: retention per plan, a durable store (today it is bounded and in process), storage cost limits, deletion on request | M |
| **Analytics** | Per-room persistent aggregates (blocks and warnings by scope, useful/noise votes, members active per day), a dashboard view across days, retention rules. Must stay aggregate to keep the privacy posture | M |
| **Slack integration** | The in-progress webhooks may be enough. A Slack app (OAuth install, slash commands) is more work and more support | S to M |
| **SSO and SCIM** | SAML and OIDC for dashboard and CLI sign-in, a SCIM endpoint for provisioning and deprovisioning, mapping identity-provider groups to rooms | L |
| **Audit logs** | An append-only per-org log of joins, approvals, policy changes, webhook changes and key events, with export; retention per plan | M |
| **E2E key management** | Key rotation without a new room, per-member key wrapping so a member can be removed, org-held keys or a KMS integration. Needs a cryptography design review before code | L |
| **On-prem support, SLA** | Mostly not code: support process, versioned releases with a support window, on-call. Code: a status page and alerting for the hosted relay, and multi-region guidance | M |
| **Hosted relay itself** (needed for the free tier too) | Raise `MAX_ROOMS` (100 live rooms per process today) or scale out with Redis, abuse handling for public room creation, terms of service and a privacy policy, a decision on `GEMINI_API_KEY` (captions send cleartext prompts and diffs to Google's API) | M |

## Open questions

Each needs an owner and a decision before any paid feature is built.

1. **What is a member, and what is a seat?** Today a member is one checkout's
   daemon connection, so one person with two checkouts is two members. Is
   the free tier's limit of 5 counted in people, machines or agent
   identities? Is Team's "per user" the same unit?
2. **Free tier without accounts?** The hosted free tier could keep today's
   no-signup rooms (best for Show HN, hackathons and the 60-second
   time-to-first-room target) with limits enforced per room, or require
   sign-in. Without accounts, per-room limits are easy to work around by
   opening a second room.
3. **5 or 6?** The relay's hard cap is 6 today. Keep 6 for free, or lower it
   to the plan's 5?
4. **Open source or open core?** Everything is Apache-2.0 today, so a
   self-hoster gets every feature that is in the repo. Are paid features
   only properties of the hosted service (history storage, uptime, support),
   or is some code (SSO, audit logs, key management) kept out of the open
   repository or under another license? This decides where the Team and
   Enterprise code lives.
5. **History retention numbers.** How many hours or days per tier, and does
   the free hosted tier get any? The in-progress history is opt-in per room.
6. **Is Slack a paid feature** when generic webhooks are in the open-source
   relay? If webhooks merge as written, any self-hoster has them.
7. **Analytics in e2e rooms.** Decision counts work on hashes, but anything
   that names files or symbols cannot be computed by the relay. Is that
   acceptable for paid analytics?
8. **AI captions on the hosted relay.** Off (no third party sees code), on
   for Team only, or opt-in per room? Who pays for the API calls?
9. **Data residency.** One region to start? Enterprise buyers will ask.
10. **Free Team for hackathons, education and open-source projects?** The
    hackathon playbook currently offers a free relay per event.
11. **Trials, annual pricing, minimum seats.** Defaults for a first version.
12. **Who runs support and on-call** behind an SLA?

## Before any of this is built

Validate demand first with what can be measured without telemetry: hosted
relay rooms per week, rooms that reach 4 or more members (the ones a 5-member
free limit would affect), and inbound questions about SSO or audit logs. See
the success metrics in [README.md](README.md#success-metrics).
